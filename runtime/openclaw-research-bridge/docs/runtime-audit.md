`sessionId` is ephemeral and may change on `/new` or reset. The private `main` agent ID alone does not prove private chat: existing routing can place a group under `main`. The bridge requires the exact trusted route tuple plus a positive private Telegram chat ID matching its sender. Current missing runtime identity fields remain a deployment blocker; persisted routing metadata is useful for configuration review but cannot repair a missing live factory context.

Source compatibility checks cannot prove that every actual run receives the expected context, that Claude selected a tool, or that a provider ran a specific underlying model. Those require separately authorized runtime acceptance checks after the host context gap is fixed.

## Unapplied context propagation candidate

`src/runtime-patch.mjs` exports the pure function `createRuntimeContextPatch({grantSource,resolutionSource})`. It checks three exact, unique source anchors, rejects repeated application, and returns candidate source text, before/after SHA-256 values and small review excerpts for two files. It never reads or writes files and is not an installation command. Review excerpts deliberately are not executable `patch` instructions. The caller must pin the installed version and source hashes before considering a separately authorized deployment.

The required chain is:

1. Telegram's channel implementation sends `conversation.id: String(chatId)` and trusted sender metadata to the standard inbound builder (`dist/bot-message-nRw-6GtF.mjs:784`). The builder produces `ChatId`/`SenderId`, while `ChannelContext` is only the caller's optional field (`dist/run-channel-turn-yi_2BMWy.mjs:325` and `:348`). This Telegram call does not populate that optional field.
2. Run construction sets `chatId` from `sessionCtx.NativeChannelId ?? sessionCtx.ChatId` and sender metadata from `sessionCtx.SenderId` (`dist/agent-runner-utils-CoB_zQdE.mjs:363` and `:379`). Those contexts are expanded into run parameters (`dist/agent-runner.runtime-BVB4SNqA.mjs:2322` and `:2332`) and the CLI receives those run parameters (`:1550`). `prepare.runtime-DHNpINUz.mjs:1049` passes them to `buildCliMcpGrantContext`.
3. Existing grant construction preserves `run.senderId` but reads chat ID only from the optional `run.channelContext.chat.id`. Candidate change 1 passes the already trusted `run.chatId` into this helper. Explicit ChannelContext values are retained. A conflict between either existing sender/chat field and the corresponding run field throws the fixed `MCP_CHANNEL_CONTEXT_CONFLICT` code rather than choosing one identity. No recipient string, message text, alias or child header is parsed.
4. Candidate change 2 passes the grant's `channelContext.chat.id` and `.sender.id` into `createOpenClawTools` as `nativeChannelId` and `requesterSenderId`. Missing values stay missing. Positive private chat/sender equality and the exact configured tuple are still enforced by the plugin.

Merely forwarding two factory fields is insufficient when the earlier Telegram chat ID was dropped. The generator therefore touches both `dist/mcp-grant-context-Cevi5zD3.mjs` and `dist/tool-resolution-BgF9x3jL.mjs`. It does not weaken model, owner, session, channel or group policy.

The installed-runtime suite evaluates the patched real grant helper, real grant construction, the complete patched factory-options expression and the actual compiled plugin-context helper in isolated VM contexts with synthetic inputs. It verifies private context acceptance, absent identity rejection, owner messages in negative-ID groups rejection, route mismatch rejection, explicit context retention and conflict rejection. This is local functional validation of a candidate patch; it does not assert live compatibility, approval to modify installed OpenClaw or permission to activate the plugin.
