# Research Candidate Bridge

This is a **local, disabled-by-default research plugin**. The reviewed private/group pilot and exact group collaborator permissions are deployed; owner private and group submit/propose/get passed real inbound acceptance. 协作者’s own inbound acceptance remains separate. This revision adds host-observed execution records using the existing gateway service lifecycle. The four tools still do not send Telegram messages, invoke a model, verify evidence, commit a decision or place a trade.

| Tool | Local host command | Purpose |
| --- | --- | --- |
| `research_task_submit` | `task-submit` | Persist unverified sources, a research question and versioned thesis/skill/strategy context. |
| `research_task_get` | `task-get` | Read one task in the host-selected private or isolated group test scope. |
| `research_task_list` | `task-list` | Read paginated task summaries. |
| `research_task_propose` | `task-propose` | Save decision/prediction analysis as a candidate. |

All request objects are strict, including nested objects. The model cannot supply scope, environment, owner, approval, actual model, usage or verification fields. Source text is untrusted data; even `kind: "fact"` does not verify it. Decision labels `buy` and `sell` remain research candidates and do not authorize execution.

`research_task_get` accepts `{taskId}`. If the host returns `projection: "summary"`, use its `detailRetrieval` references: `{taskId,detail:"source"|"evidence"|"proposal",itemId}` retrieves one complete item. Source item IDs are their `evidenceId`, evidence item IDs are their `id`, and proposal item IDs are their `id`. `{taskId,detail:"publication"}` reads publication without an item ID. An item ID without detail, a missing item ID for a source/evidence/proposal, and an item ID on publication are rejected. Full detail is the item itself; it carries no new approval or verification.

The JSON schemas are in `src/schema.mjs`; the workflow validates timestamps, source uniqueness and persisted state again. Strings have UTF-8 byte limits, whole requests are limited to 60 KiB, and responses to 512 KiB. The host reserves envelope space with a 400 KiB result bound and projects large tasks into summaries with per-item retrieval. The final bridge bound remains a guard against unexpected oversized host results and returns a fixed error rather than truncated evidence. In such an exceptional failure the preceding local operation may already have succeeded; reuse its exact idempotency key or read it back. Source locators are inert strings, not automatic fetch instructions.

## Authorization and configuration

The SDK-free `registerResearchBridge(api, {createHost})` uses `api.pluginConfig` and a synchronous tool factory. `validateBridgePolicy(config)` validates trusted configuration and existing directory metadata without registration or host creation. Private tools retain the existing rules:

- `agentId === "main"`, `messageChannel === "telegram"`, `senderIsOwner === true`;
- nonempty `sessionId`, and an exact configured `sessionKey`;
- `nativeChannelId` and `requesterSenderId` are matching positive numeric strings;
- the complete `{sessionKey,nativeChannelId,requesterSenderId}` tuple appears in `allowedContexts`.

Group access requires a separate, optional `allowedGroupContexts` array of exact `{sessionKey,nativeChannelId,requesterSenderId}` tuples. The observed group route is `agent:main:telegram:group:<negative-chat-id>`; the configured session key must exactly match its negative numeric chat ID. The positive sender ID must already be an approved private owner in `allowedContexts`. Runtime `agentId === "main"`, `messageChannel === "telegram"`, `senderIsOwner === true` and nonempty `sessionId` are still mandatory. Authorization applies to the configured owner in that exact group, not every group member or every group the owner joins.

Non-owner collaboration uses the separate optional `allowedGroupCollaboratorContexts` array, with the same exact triple shape and at most 20 entries. Each collaborator must be assigned to a group/session already present in `allowedGroupContexts`, and their positive sender ID must not appear in the private owner list. The trusted runtime must supply `senderIsOwner === false` explicitly; missing, string, numeric or unexpectedly true values do not qualify. Common `main`/Telegram/session checks and topic denial still apply. Collaborators are not added to `allowedContexts` or `commands.ownerAllowFrom`, and the adapter never changes the owner bit.

A configured collaborator can use only the same four candidate tools within that group, including reading the owner’s group research and proposing analysis. The owner can read the collaborator’s group submissions and candidates. Existing group data and idempotency keys are shared; use distinct stage-specific keys for distinct requests. Scope hashing remains unchanged, so adding a collaborator creates no new group namespace and migrates no data. Actor hashes retain the actual sender/session identity and distinguish owner from collaborator. Private research, other groups, verification, approval, publication and trading are not granted.

Unlisted groups or members, channel/session aliases, account variants, topic/thread suffixes and any non-null `deliveryContext.threadId` are rejected. Missing fields, wildcards, numbers instead of strings, or prefixed IDs are rejected. No field is reconstructed from tool text, display names or delivery targets. `nativeChannelId` is the trusted platform conversation ID; `messageChannel` is the channel name. Existing routing to `main` is unchanged.

Configuration has `enabled` (default false), `environment` (only `test`), `stateDirectory`, the existing nonempty `allowedContexts`, optional nonempty `allowedGroupContexts`, and optional nonempty `allowedGroupCollaboratorContexts` (each at most 20 exact tuples). Omitting collaborator configuration preserves the previous owner-only group policy; omitting both group fields preserves private-only access. The directory must be an absolute normalized path ending in `research-bridge-test`. Existing path components cannot be symlinks. An existing final directory must be owned by the process UID with permissions 0700; the core store additionally checks private files and scope. New installations require a dedicated root, never a workspace, memory or skills directory. This collaborator update retains the existing stateDirectory and the existing group namespaces; it does not migrate, copy or overwrite private or group records. The review plan supplies the eventual exact route; no production identifiers are included here.

The manifest declares precisely the four tools in `contracts.tools` and `activation.onStartup: true`. Startup only imports and registers definitions; it does not open a research database or run a task. These declarations are required by the installed native loader. Registration is `optional: true`. A reviewed activation also needs exact tool names in the agent's `tools.alsoAllow`, subject to every other global/provider/agent/group/sandbox deny rule. Existing tool policy must be preserved. No `llm_input`, `llm_output` or conversation hook opt-in is needed by this adapter.

The private host remains `{agentId:"main",environment:"test",mode:"agent"}`. Each group uses `agentId = "tg-group-" + SHA256(JSON.stringify(["research-bridge-group-v1", trustedSessionKey, trustedChatId]))`, with the same fixed test environment and agent mode. The resulting 73-character opaque namespace separates research databases, task IDs, idempotency keys, evidence and proposals from private state and other groups. It is stable across `/new` and does not migrate or overwrite existing private data. Model inputs cannot supply scope or select this namespace. Cross-scope task reads return `NOT_FOUND`.

This is research-record isolation, not whole-workspace, agent-routing or OS isolation. The existing `main` agent, filesystem tools and same-UID access retain their existing permissions; group-visible research output can be seen by that group. These application rules do not protect against native shell access, local operators or installed plugins. Enabling research collaboration does not change general assistant, control-command, filesystem or owner permissions. The host is opened for each call and always closed. Actor attribution is a SHA-256 hash of the trusted sender and ephemeral session ID; raw IDs are not passed as actor IDs. `/new` changes that attribution hash while preserving the group namespace. Factory context/config is snapshotted for the runtime-owned tool lifecycle.

## Runtime compatibility and remaining acceptance

OpenClaw **2026.9.4** supports Claude bundle MCP and the SDK declares the required identity fields. Its original installed loopback tool construction omitted `nativeChannelId` and `requesterSenderId`. The private pilot includes the reviewed two-file fix: trusted `run.chatId`/sender context reaches the grant, then those fields reach the plugin factory. Existing explicit-context conflicts fail closed. Negative group IDs use the same string-preserving path; group support does not add a route, identity fallback or another host patch.

The prior installed-runtime source test describes the original-version gap and the synthetic patch checks; it is historical evidence, not a post-patch live acceptance test. The native-manifest test uses the actual installed parser, startup selector, tool planner and registry API with the real entry, including accepted configured owner/collaborator contexts and rejected unlisted-member/topic contexts. The native-registry and bundled-entry tests use the real entry and packaged host to persist synthetic research with an explicitly false-owner collaborator, read owner-created group tasks, and expose the collaborator’s candidate back to the owner with distinct actor attribution. Neither test sends messages or calls models. Real inbound tool selection and execution remain to be verified separately; keep the permission checks if a runtime field is absent.

## Existing Telegram entry and activity window

Ordinary group access and research-tool access are separate. The currently deployed `telegram-active-window` gate does not require owner identity: any sender can wake the configured group using an explicit bot mention or a reply to the bot, and other people can participate during the active window without extending the original activator’s window. Sleeping-window, human-to-human reply and other-mention suppression remain unchanged. Native Telegram `groupPolicy: "open"` does not itself require owner status, but explicit group/topic sender overrides and control-command authorization remain independent. No gate, channel policy or owner allowlist change is needed by this adapter. This is a static code finding, not proof of a particular live message’s delivery.

## Model provenance

`activeModel` is returned only as `selectedModelUnverified`. In the installed native CLI wrapper, both `llm_output.model` and synthetic `lastAssistant.model` are populated from the requested runtime selection, not an independently verified native model receipt. Output hooks can also be absent for isolated/control runs or empty assistant text and occur after tools. They cannot safely be used to certify a proposal from inside that tool call.

The bridge envelope keeps `actualModelReceipt`, `usage` and `costUsd` as `null`, with `verification: "not-attested-by-bridge"`: that tool cannot certify the model currently invoking itself. Null cost means unknown, not free. No qualitative confidence is converted into a probability. A later privileged review path must separately establish evidence, actual model provenance and accounting before publication. The bridge does not expose that path, and historical paper statistics do not guarantee future net profit.

### Host-observed execution records

Successful submit/propose calls now capture a private binding to the authorized scope, actor, exact request/result hashes and original creation time. An in-process service in the existing gateway reconciles bounded batches every 30 seconds, rotating the configured scopes; task-get also reconciles that task before reading. No additional gateway, OS service, model request, Telegram delivery or conversation-hook access is required. Registration alone does not start the service. Failed observation does not undo or misreport an already saved candidate.

The native reader accesses only the fixed main agent database and the exact Claude project/session JSONL. It verifies the OpenClaw session/window, pins a resolved native session UUID, and refuses to substitute the new session after a reset. Missing historical bindings remain unknown. The collector matches a unique native tool_use/tool_result pair to the host-captured hashes, target, actor and creation interval; the gateway MCP execution UUID is not the native tool-use ID. Source reads are bounded to 64 MiB and a ten-minute timestamp window around the original write; larger, missing, ambiguous or unsupported records remain pending/unavailable for explicit follow-up.

`research_task_get({taskId})` adds `executionEvidence`: latest records for the submission and up to 20 candidates, their status and pending count. `research_task_get({taskId,detail:"execution",itemId:executionId})` returns one complete record. These records use `verification:"host-observed-not-provider-signed"`. Requested and observed model labels remain separate; native message usage carries an accountingKey shared by all tools using the same message. Deduplicate that key rather than summing usage per candidate. The current Claude JSONL adapter records cost as unknown and does not settle or retroactively reserve budget; billing reconciliation and production model dispatch remain separate work.

Bindings and execution receipts use new private SQLite files in each existing test scope. Raw session IDs and source text never enter model-facing receipts. Records retain digest-linked revisions; the candidate remains candidate, and task.modelReceipt stays null until a separately authorized commit. Same-UID access and writable local runtime logs are not a tamper-proof or provider-signed boundary. Existing primary-group writable intermediate runtime directories are accepted only for the owning user/group; log files themselves must not be group/world writable. No directory permissions are altered.

## Packaging and tests

`index.mjs` imports the installed `openclaw/plugin-sdk/core` plus the packaged `lib/host.mjs`. The reviewed build must copy the host and its required core modules into `lib/`; the deployable plugin must be self-contained. No third-party dependency or external plugin is installed by this source directory. `src/register.mjs` and its tests are SDK-free.

The installed OpenClaw loader supplies public SDK aliases for external plugins, including native ESM resolution. A deployment through that loader therefore does not require a plugin-local `node_modules/openclaw` symlink or another SDK installation. A standalone Node import outside OpenClaw needs equivalent resolution; the opt-in smoke test uses a temporary Node resolution hook for exactly `openclaw/plugin-sdk/core` and removes it immediately after import.

Run `node test/register.test.mjs` for mock-host authorization and lifecycle regressions, and `node test/host-integration.test.mjs` in the review workspace for the real sibling core-host persistence test. The historical `test/installed-runtime.test.mjs` targets the original unpatched 2026.9.4 sources and synthetic patch execution; do not interpret its old-source assertions as current deployment acceptance. Opt-in SDK tests require filesystem read permission and are skipped when `OPENCLAW_RUNTIME_ROOT` is not supplied. Importing the installed gateway entrypoint, loading live credentials, starting a duplicate server and making paid calls are deliberately outside this test.

`OPENCLAW_RUNTIME_ROOT=/ABS/PATH/TO/OPENCLAW node test/bundled-entry.test.mjs` imports the actual default entry with the actual installed SDK and packaged `lib`, checks the bundle manifest hashes, verifies default-disabled behavior and the four optional tools under synthetic authorized context, and runs durable synthetic private/group submit/get with bidirectional cross-scope rejection. It verifies closed database handles on Linux and removes only its own temporary data. This tests the entry and dependency closure without loading the production plugin registry; real inbound acceptance remains separate.

`OPENCLAW_RUNTIME_ROOT=/ABS/PATH/TO/OPENCLAW node test/native-manifest-contract.test.mjs` tests real native manifest planning and tool registration without activating a production registry. It reproduces the previous missing-manifest-declaration failure, accepts all four repaired tool declarations, and checks explicit group authorization, unlisted-member/topic denial and non-owner collaborator persistence. The host integration test also verifies identical idempotency keys in private and two groups, durable state after session reset, cross-scope `NOT_FOUND`, shared group candidates and distinct collaborator actor attribution.

See `docs/runtime-audit.md` for the original pre-patch source audit and hook limits; its unapplied/blocker wording records that earlier audit stage.
